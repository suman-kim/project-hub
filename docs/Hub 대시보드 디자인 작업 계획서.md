# Hub 대시보드 디자인 작업 계획서

Oct 27, 2026 · @suman

## 목표와 범위

서버 뼈대(M0\~M6)로 API는 다 갖췄지만, 지금은 모든 일을 `curl`로 해야 한다. 대시보드의 목표는 **"지금 내가 처리할 일"을 한 화면에서 보고, 그 자리에서 끝내는 것**이다. 처리할 일은 답변을 기다리는 run, 실패한 run, 리뷰를 기다리는 PR, 대기 중인 기획이다.

이 계획서는 HTML 시안으로 화면을 확정하는 데까지를 다룬다. 시안이 확정되면 `apps/web` 구현 계획서를 따로 쓴다.

**이번에 하는 것**

- 화면 구성(정보 구조)과 화면별 내용, 상태(빈 화면, 로딩, 오류)
- 클릭해 볼 수 있는 HTML 시안: claude.ai 비공개 페이지로 만들어 링크로 공유
- 디자인 토큰: 색, 글꼴, 간격, 상태 색
- UI를 붙이려면 서버에 더 필요한 것 목록 (구현은 다음 단계)

**이번에 하지 않는 것**

- `apps/web` 구현과 서버 보강 구현
- 권한 요청을 화면에서 승인하는 흐름(`--permission-prompt-tool`), PR 머지 자동화, 알림
- 밖에서 접속(Tailscale)과 모바일 전용 화면: Hub는 `127.0.0.1`에만 열려 있어 맥북 브라우저에서만 쓴다

**완료의 정의**

1. 모든 화면의 시안이 하나의 클릭 가능한 페이지로 있고, 아래 "사용 장면" 7가지를 시안 안에서 끝까지 따라갈 수 있다.
2. 디자인 토큰(라이트·다크)과 상태 색이 확정되어 있다.
3. "서버 보강" 목록이 확정되어 구현 계획서로 넘길 수 있다.

## 사용 장면

사용자는 한 명(나)이고, 맥북 브라우저에서 `http://127.0.0.1:2424`를 연다. 화면은 아래 6가지 일을 빠르게 끝내는 데 맞춘다.

| # | 장면 | 지금 쓰는 API |
| --- | --- | --- |
| 1 | 아침에 열어 밤사이 생성된 기획을 읽고 승인·수정 요청·반려한다 | `GET /api/ideas`, `POST /api/ideas/:id/approve·revise·reject` |
| 2 | task를 골라 실행하고, 로그를 지켜보다가 질문이 오면 답한다 | `POST /api/tasks/:id/run`, `GET /api/runs/:id/logs`, `POST /api/runs/:id/answer`, WebSocket |
| 3 | PR이 생긴 task를 확인하고, GitHub에서 머지한 뒤 `done`으로 바꾼다 | `GET /api/tasks?status=review`, `PATCH /api/tasks/:id` |
| 4 | 실패한 run의 사유를 보고 다시 실행하거나 task 메모를 남긴다 | `GET /api/tasks/:id/runs`, `GET /api/runs/:id` |
| 5 | 앱 설정(방향성 메모, 자동 생성 주기, 허용 도구)과 작업 규칙을 고친다 | `PATCH /api/apps/:id`, `PUT /api/rules` |
| 6 | 이번 달 비용과 구독 사용량을 확인한다 | `GET /api/costs`, `GET /api/costs/monthly` |
| 7 | 새 앱 기획을 읽고 마음에 드는 후보를 더 파 본 뒤 승인한다. 폴더, GitHub 저장소, 세션이 만들어지는 과정을 보고, 세션은 claude.ai나 Claude 앱에서 이어서 본다 | `POST /api/concepts/generate`, `POST /api/ideas/:id/develop`, `POST /api/ideas/:id/approve {app}`, `GET /api/runs/:id`, `POST /api/apps/:id/bootstrap` |

## 설계 원칙

- **처리할 일이 먼저 보인다.** 우선순위는 답변 대기(`input`) → 실패한 run → 리뷰 대기 → 대기 중 기획 → 실행 중 run 순이다.
- **새로고침하지 않는다.** WebSocket 이벤트를 받으면 해당 항목만 다시 읽는다. 연결이 끊기면 화면 위에 표시하고 다시 붙는다.
- **개발 도구답게 조밀하게 만든다.** 카드보다 목록 행을 기본으로 한다. task ID와 브랜치, 경로는 고정폭 글꼴로 쓴다. 자주 쓰는 동작에는 단축키를 둔다.
- **허용된 동작만 누를 수 있다.** 상태 전이 규칙(`packages/shared/src/status.ts`)을 화면에서도 그대로 써서, 지금 갈 수 없는 상태 버튼은 비활성으로 둔다.
- **되돌리기 어려운 동작은 확인을 받는다.** run 중지, 기획 반려, task 취소, 규칙 저장(파일을 다시 씀)이 여기에 해당한다.
- **한국어로 쓰되, 상태 값은 서버와 1:1로 맞춘다.** 화면에 보이는 이름은 한국어로 쓰고, 그 아래 값은 서버 enum과 똑같이 둔다.

| 상태 값 | task 화면 이름 | run 화면 이름 | 기획 화면 이름 |
| --- | --- | --- | --- |
| `todo` / `queued` / `pending` | 할 일 | 대기 | 검토 대기 |
| `doing` / `running` / `revising` | 진행 중 | 실행 중 | 수정 중 |
| `input` | 답변 대기 | 답변 대기 | – |
| `review` | 리뷰 | – | – |
| `done` / `approved` | 완료 | 완료 | 승인 |
| `cancelled` / `stopped` / `rejected` | 취소 | 중지 | 반려 |
| `failed` | – | 실패 | – |

## 지금 데이터의 모양

시안에는 지금 DB의 실제 모양을 반영한다. 데이터 양이 화면 구성에 직접 영향을 준다.

| 항목 | 지금 값 | 화면에 주는 영향 |
| --- | --- | --- |
| 앱 | LK, HR, CM, OA, TH, FJ(새 앱 기획으로 만든 앱). OA는 저장소 경로가 없다 | 저장소가 없는 앱은 실행·기획 생성 버튼 대신 "저장소 경로를 설정하세요"를 보여 준다 |
| task | LK 270개(완료 190, 진행 중 24, 할 일 47, 리뷰 4, 취소 5), CM 26개, TH 4개, HR·OA 0개 | 완료·취소는 기본으로 접는다. 칸반 한 열에 수십 개가 쌓이므로 기본 보기는 상태별 목록이다 |
| task 설명 | 평균 530자, 최대 3,000자. Task Master에서 가져온 markdown | 상세에서 markdown으로 렌더링한다. 목록에서는 첫 줄만 보여 준다 |
| task 메모 | `metadata.notes[]`에 상태 변경과 run 결과 요약(markdown)이 쌓인다 | 상세 화면의 타임라인으로 쓴다 |
| run | 종류는 `implement`와 `idea_gen`. 비용, 브랜치, worktree, 질문, 실패 사유, 사용량을 담는다 | run 화면의 머리 정보 |
| run 로그 | 종류는 `hub`(Hub 단계), `system`, `assistant`, `tool_use`, `tool_result`, `result`, `stderr`, `rate_limit`. 한 run에 수십\~수백 줄 | 종류별로 모양을 다르게 한다. `tool_result`는 접는다 |
| 기획 | 문제, 제안, 시나리오, 명세, 영향 범위, 예상 task(크기, 의존 관계)와 버전 이력. 종류는 기능 기획(`feature`)과 새 앱 기획(`app`) | 기획 상세는 문서처럼 읽히게 한다. 버전끼리 비교할 수 있게 한다 |
| 새 앱 세션 | `claude agents --json`의 항목: 짧은 ID(`758307a0`), 이름("FJ 벌금통"), 폴더, 상태(`running`, `waiting`), 기다리는 이유(`input needed`). Remote Control 링크(`claude.ai/code/session_...`)는 세션 화면 출력에만 나온다 | 세션은 Hub 밖에서 돌기 때문에, Hub는 상태를 읽어 보여 주기만 하고 답은 claude.ai나 Claude 앱에서 하게 한다 |
| 새 앱 기획 | 위에 더해 한 줄 소개, 대상 사용자, MVP 기능, 비슷한 서비스(링크), 시장, 수익 모델, 기술 스택, 리스크, 수요 검증, 제안 앱 코드·이름·폴더, 다른 후보 2\~4개, 출처. 승인 전에는 앱이 없다 | 기획함 안에 "새 앱" 탭을 따로 둔다. 비슷한 서비스와 출처는 링크로 보여 준다 |
| 사용량 | 5시간·7일 창별 소진율과 초기화 시각. run이 돌 때만 갱신된다 | 값 옆에 "언제 받은 값인지"를 같이 보여 준다 |

WebSocket(`/ws`)은 `run.log`, `run.status`, `task.updated`, `idea.created`, `idea.updated`, `app.updated`, `session.event`를 보낸다. 페이로드 타입은 `packages/shared/src/events.ts`에 있다.

## 정보 구조

&#91;화면 구조: 왼쪽 사이드바(앱 선택 + 메뉴) · 위 상태 막대(실행 중 run 수, 사용량, 연결 상태) · 본문\]

- **왼쪽 사이드바**: 위쪽에 앱 선택(전체, LK, HR, CM, OA, TH)을 두고, 아래에 메뉴(오늘, task, 기획, 비용, 규칙, 앱 설정)를 둔다. 앱을 고르면 모든 화면이 그 앱으로 걸러진다.
- **위 상태 막대**: 실행 중인 run 수, 7일 사용량 막대(80% 기준선 표시), WebSocket 연결 상태, 명령 팔레트(⌘K)를 둔다.
- **본문**: 목록과 상세를 함께 보여 준다. 상세는 오른쪽 패널로 열어 목록 위치를 잃지 않게 한다. run 로그는 넓게 봐야 해서 따로 연다.

## 화면

### S1. 오늘 (첫 화면)

처리할 일을 한곳에 모은 화면이다. 칸마다 그 자리에서 끝낼 수 있는 동작을 붙인다.

| 칸 | 내용 | 바로 할 수 있는 동작 |
| --- | --- | --- |
| 답변 대기 | run의 질문 전문, task 제목, 기다린 시간 | 답변 입력과 보내기 (같은 세션으로 재개) |
| 실패한 run | 실패 사유(사용량 한도, 프로세스 오류, 커밋 없음, push·PR 실패), 시각 | 다시 실행, 로그 보기 |
| 리뷰 대기 | PR 링크, 브랜치, run 결과 요약 첫 줄 | PR 열기, 완료로 바꾸기 |
| 대기 중 기획 | 제목, 앱, 문제 한 줄, 예상 task 수 | 기획함에서 열기 |
| 실행 중 | task, 경과 시간, 마지막 로그 한 줄 (실시간) | 로그 보기, 중지 |
| 새 앱 세션 대기 | 세션 이름, 앱, 기다린 시간. 예: "FJ 벌금통이 디자인 시스템 선택을 기다린다" | Remote Control 링크 열기, `claude attach <ID>` 복사 |

처리할 일이 없으면 "처리할 일이 없습니다"와 함께 최근 완료된 run 몇 개를 보여 준다.

### S2. task 목록

- **기본 보기**: 상태별로 묶은 목록. 순서는 답변 대기 → 진행 중 → 리뷰 → 할 일이고, 완료와 취소는 접어 두며 최근 20개만 보여 준다. 칸반 보기로 바꿀 수 있다.
- **행에 보이는 것**: ID(`LK-12`), 제목, 크기(S/M/L), 태그, 의존 상태, PR 여부, 실행 중 표시.
  - 의존하는 task 중 완료되지 않은 게 있으면 "막힘"으로 표시한다.
- **필터**: 앱, 상태, 태그, 크기, 제목 검색.
- **만들기**: 제목, 설명, 크기, 의존 task를 받는다(`POST /api/tasks`).
- **가져오기**: 앱 설정 화면에 Task Master 가져오기 버튼을 둔다(`POST /api/import/taskmaster`).

### S3. task 상세 (오른쪽 패널)

- **머리**: ID, 제목, 상태 버튼(허용된 전이만 활성), 실행 버튼, PR 링크, 브랜치.
- **본문**: 설명(markdown), 의존 관계(앞뒤 task와 각 상태), 연결된 기획.
- **문서**: 기획 명세와 인수인계 문서 목록. 누르면 본문을 연다.
- **타임라인**: `metadata.notes`를 시간순으로 보여 준다. 상태 변경, run 결과 요약, 직접 쓴 메모가 섞인다. 메모를 남기면 상태는 그대로 두고 기록만 추가된다.
- **run 목록**: 상태, 시작 시각, 걸린 시간, 비용. 누르면 S4로 간다.

### S4. run

- **머리**: 상태, task, 종류, 브랜치, worktree 경로, 비용, 시작·종료 시각, 중지 버튼.
- **질문 카드**: 상태가 답변 대기일 때 맨 위에 질문과 답변 입력란을 둔다. 지금까지 보낸 답변 기록도 같이 보여 준다.
- **로그**: 실시간으로 이어 붙인다. 아래로 따라가기를 켜고 끌 수 있다.

| 로그 종류 | 모양 |
| --- | --- |
| `hub` | Hub가 한 단계(worktree 생성, push, PR 생성). 굵은 단계 표시 |
| `assistant` | Claude의 말. 본문 글꼴 |
| `tool_use` | 도구 이름과 대상 한 줄. 고정폭 |
| `tool_result` | 접힌 상태로 둔다. `[오류]`로 시작하면 빨간 표시 |
| `stderr`, `rate_limit` | 경고 색 |
| `result` | 마지막 요약(턴 수, 비용) |

- **결과**: 끝나면 결과 요약(markdown)을 보여 준다. 실패했으면 사유와 "다시 실행" 버튼을 보여 준다.

### S5. 기획함

- **목록**: 상태 탭(검토 대기, 수정 중, 승인, 반려)과 앱 필터. 행에는 제목, 앱, 버전, 만든 시각, 자동 생성 여부를 보여 준다.
- **상세**
  - 본문: 문제, 제안, 시나리오, 명세, 영향 범위를 문서처럼 읽히게 보여 준다.
  - 예상 task: 크기와 의존 화살표를 붙인다. 승인하면 이대로 task가 만들어진다는 걸 미리 보여 준다.
  - 버전: 버전을 바꿔 볼 수 있다. 바로 앞 버전과 무엇이 바뀌었는지 강조하고, 각 버전의 수정 요청 내용을 붙인다.
- **동작**: 승인, 수정 요청(요청 내용 입력), 반려(사유 입력).
  - 반려 사유는 다음 생성 때 프롬프트에 들어간다고 입력란에 안내한다.
  - 수정 중일 때는 동작을 잠그고 진행 중인 생성 run으로 가는 링크를 보여 준다.
- **즉시 생성**: 앱과 방향성 메모를 고르고 생성한다. 이미 생성 중이면 버튼을 잠근다(서버가 409를 돌려준다).

### S5-1. 새 앱 기획 (기획함의 "새 앱" 탭)

- **목록**: 기능 기획과 같은 상태 탭. 행에는 제목, 한 줄 소개, 버전, 만든 시각, 자동 생성 여부를 보여 준다. 앱 열은 승인 뒤에 생긴 앱 코드를 보여 준다.
- **상세**
  - 머리: 제목, 한 줄 소개, 대상 사용자.
  - 본문: 문제, 해결 방식, MVP 핵심 기능, 시나리오, MVP 명세를 보여 준다.
  - 조사: 비슷한 서비스 표(이름·링크·차이), 시장, 출처 링크를 둔다. 웹 조사로 채운 칸이라는 걸 표시한다.
  - 사업: 수익 모델, 리스크, 수요 검증 방법.
  - 다른 후보: 카드 2\~4개. "이걸로 깊게 기획"을 누르면 새 기획 생성 run이 시작된다(`develop`).
- **승인 창**: 제안된 앱 코드·이름·폴더를 보여 주고 고칠 수 있게 한다. 승인하면 생기는 것을 미리 보여 준다.
  - 만들어질 것: `~/project/<폴더>`, GitHub 비공개 저장소 `<소유자>/<폴더>`, task 목록, claude --rc 세션.
  - 코드가 겹치거나 폴더가 이미 있으면 서버가 거부하므로, 입력하는 동안 바로 알려 준다.
- **시작 진행 화면**: 승인 뒤 bootstrap run의 단계를 체크리스트로 보여 준다.
  - 단계: 폴더·첫 커밋 → GitHub 저장소 → 작업 공간 신뢰 → 세션 시작. 각 단계는 run 로그의 `hub` 줄로 갱신한다.
  - 끝나면 저장소 링크, 세션 이름과 ID("FJ 벌금통" · `758307a0`), Remote Control 링크를 보여 준다. 터미널용 `claude attach <ID>` 복사 버튼도 둔다.
  - 세션 상태(실행 중, 입력 대기, 끝남)를 함께 보여 준다. 세션은 첫 단계로 UI 디자인을 만들면서 디자인 시스템 선택처럼 사용자에게 묻고 멈추므로, 입력 대기면 눈에 띄게 표시한다.
  - 디자인 시안 링크와 질문 내용은 세션 안에만 있다. 이 화면은 "세션에서 확인하세요"로 안내만 한다.
  - 세션을 못 띄워 runner로 대신 시작했으면 그 사유와 runner run 링크를 보여 준다. 실패하면 사유와 "다시 시도" 버튼(`POST /api/apps/:id/bootstrap`)을 둔다.
- **즉시 생성**: 이번에만 덧붙일 요청을 입력하고 생성한다. 웹 조사가 항상 들어가 기능 기획보다 오래 걸리고 비용이 크다는 걸 버튼 옆에 적는다.

| 상태 | 처리 |
| --- | --- |

## 시안 작업 방식

- **형태**: 클릭해 볼 수 있는 HTML 시안 하나에 모든 화면을 담는다. 사이드바를 누르면 화면이 바뀌고, 버튼을 누르면 상태가 바뀌는 흉내를 낸다. 서버에는 붙지 않는다.
- **공유**: claude.ai 비공개 페이지로 만들어 링크로 드린다. 같은 링크를 계속 갱신하고, 피드백은 대화나 페이지 댓글로 받는다.
- **예시 데이터**: 지금 DB의 모양(앱 5개, LK의 task 분포, 실제 로그 종류, TH 기획 #1)을 따르되, 문장은 예시용으로 바꿔 넣는다. 각 저장소의 실제 task 내용은 페이지에 올리지 않는다.
- **단계별 공유**: 한 번에 다 만들지 않고, 아래 작업 단계마다 공유해 방향을 확인한 뒤 다음으로 넘어간다.

## 리스크

- **LK 진행 중 24개의 정체**: Task Master의 `in-progress`를 그대로 옮긴 것이라, 실제로 진행 중인 일이 아닐 수 있다. 화면을 열면 "진행 중"이 가득 차 보인다. 디자인 문제가 아니라 데이터 정리 문제이므로, 시안을 보기 전에 정리할지 정한다.
- **task 설명의 형식이 제각각**: Task Master에서 온 설명은 markdown 형식이 고르지 않다. 렌더링이 깨지는 경우를 시안 예시에 하나 넣어 확인한다.
- **새 앱 세션은 Hub 밖에 있다**: 세션의 질문과 디자인 시안은 Remote Control로만 오가고, Hub는 `claude agents --json`과 `claude logs`로 상태를 읽을 뿐이다. 이 두 명령의 출력 형식이 바뀌면 상태 표시가 깨질 수 있어, 못 읽으면 "상태를 알 수 없음"으로 보여 준다.
- **사용량 값이 오래될 수 있다**: Hub가 claude를 실행할 때만 값을 받으므로, 오래 쉬면 실제와 다르다. 값 옆에 받은 시각을 꼭 보여 준다.
- **시안과 실제 데이터의 차이**: 시안은 서버에 붙지 않는다. 구현 첫 단계에서 실제 데이터를 붙여 오늘·task 화면부터 다시 확인한다.
