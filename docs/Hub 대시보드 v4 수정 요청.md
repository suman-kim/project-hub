# Hub 대시보드 v4 수정 요청

Oct 28, 2026 · @suman

## 이 문서는

디자인 에이전트에게 넘기는 v4 요청이다. 정본 `design/Hub Dashboard v3.dc.html`은 그대로 두고, Hub를 **내가 개발하는 모든 앱의 통합 관리 시스템**으로 넓히면서 필요해진 **앱 페이지**를 더한다.

- **서버**: 이 문서의 데이터는 모두 서버에 이미 있다. 괄호 안의 이름은 API 필드 이름이다. 시안에 서버에 없는 값을 지어내지 않는다.
- **배경**: `docs/Hub 통합 관리 확장 계획서.md`
- **v3에서 그대로 두는 것**: 오늘, 태스크 보드, 기획 인박스(새 앱 탭 포함), 실행 기록·상세, 새 앱 세션, 규칙, 비용, 로그인, 디자인 토큰. 아래 3장에 적은 곳만 고친다.
- **작업 순서**: 1장(구조) → 2장(앱 페이지) → 3장(기존 화면 수정) 순으로 하고, 단계마다 공유한다.

## 1. 정보 구조

- **사이드바 앱 목록**: 앱을 누르면 **앱 페이지**로 간다. 지금은 앱을 누르면 다른 화면을 걸러 보는 필터인데, 이 역할은 화면 위쪽의 앱 필터로 옮긴다.
- **기능별 화면**: 오늘, 태스크 보드, 기획 인박스, 실행 기록, 비용, 규칙은 "모든 앱을 가로질러 보는 화면"으로 남는다.
- **앱 설정 화면**: v3의 앱 설정 상세는 앱 페이지의 **설정 탭**으로 옮긴다. 앱 목록과 "새 앱 기획 설정"은 메뉴의 "앱 관리"(또는 설정)에 남긴다.
- **사이드바 앱 이름 옆**: 점 색(1장 표)과 진행 상태를 붙인다. 보관한 앱은 맨 아래 "보관" 묶음으로 접는다.

**점 색** (`signals.dot`): 가장 급한 신호 하나만 보여 준다.

| 값 | 색 | 언제 |
| --- | --- | --- |
| `risk` | 빨강 | 운영·스토어 최근 배포가 실패, 또는 치명·높음 버그가 열려 있음 |
| `attn` | 주황 | 답변을 기다리는 실행, 실패한 실행, 허락을 기다리는 세션이 있음 |
| `prog` | 파랑 | 실행 중 |
| `quiet` | 회색 | 14일 넘게 조용함, 또는 멈춤·보관 |
| `ok` | 표시 없음 | 그 밖 |

## 2. 앱 페이지

### 2-0. 공통 머리

- **기본 정보**: 앱 코드와 이름, 한 줄 소개(`description`).
- **진행 상태 배지** (`lifecycle`): 누르면 바꾸는 메뉴가 열린다. 개발 중 / 운영 중 / 멈춤 / 보관.
- **현재 단계** (`stage`): 단계 막대로 보여 준다. 예: "개발 (3/6)". 단계를 누르면 그 단계로 옮긴다.
- **알림** (`signals.nudge`): 있으면 머리 아래 띠로 보여 준다. 예: "97일째 조용해요. 계속할까요, 멈춤으로 둘까요?"
  - 버튼: "계속" (닫기), "멈춤으로" (진행 상태를 멈춤으로 바꾸기)
- **링크** (`links`): GitHub, 운영 주소, App Store, Play 스토어, 문서를 아이콘 링크로 둔다.
- **탭 8개**: 개요 · 개발 · 내 할 일 · 버그 · 단계·배포 · 히스토리 · 기획 · 설정. 개발·내 할 일·버그 탭에는 열린 개수를 표시한다.

### 2-1. 개요 (`GET /api/apps/:id/overview`)

| 칸 | 내용 |
| --- | --- |
| 숫자 | 열린 개발 task(`counts.tasks`), 열린 버그(`counts.bugs`, 치명·높음이 있으면 빨강), 내 할 일(`counts.todos`, 기한 지난 것 `counts.overdueTodos`는 주황), 이번 달 비용(`costThisMonthUsd`) |
| 신호 | 막힘(답변 대기 실행·실패한 실행·허락 대기 세션 수), 실행 중 수, 마지막 활동("2일 전", `signals.activity`) |
| 최근 배포 | 저장소·환경마다 가장 최근 배포 하나(`latestDeployments`): 저장소 이름, 환경, 상태, 버전, 시각. 실패는 맨 위에 빨강으로 |
| 다음 할 일 | 내 할 일 3개(`nextTodos`), 기한이 가까운 순. 체크하면 완료 |
| 최근 히스토리 | 5줄(`recentActivities`). "히스토리 전체 보기" |
| 새 앱 세션 | 이 앱 폴더에서 도는 Hub 밖 세션이 있으면 카드로 보여 준다(v3 새 앱 세션 화면과 같은 정보). 허락을 기다리면 주황 |
| 저장소 | 저장소 목록(`repos`): 이름, GitHub, 기본 브랜치. 여러 개면 모두 |

### 2-2. 개발

- **내용**: v3 태스크 보드를 이 앱만 보이게 한 것이다. 담당이 Claude(`assignee: claude`)인 기능·잡무 task를 보여 준다.
- **저장소가 여러 개인 앱**(하루알바, cyphers-meta):
  - 카드에 저장소 이름(backend, frontend)을 붙인다.
  - 저장소 필터를 둔다.
  - 저장소가 정해지지 않은 task의 "실행" 버튼은 "저장소를 먼저 고르세요"로 바꾼다. 서버가 409를 돌려준다.

### 2-3. 내 할 일

- **내용**: Claude가 아니라 내가 직접 할 일(`assignee: me`)이다. 예: 스토어 심사 제출, 도메인 연결, 결제 계정 만들기, 디자인 확인.
- **목록 모양**: 체크리스트처럼 가볍게 보여 준다.
  - 행: 제목, 기한(`dueDate`, 지나면 주황), 우선순위(`priority` 1\~3), 단계(`stage`), 만든 사람(직접 / Claude가 남김)
  - 체크하면 바로 완료된다. 리뷰 단계가 없고, 완료를 해제하면 다시 할 일이 된다.
  - 실행 버튼은 없다. 서버가 내 할 일은 실행하지 않는다.
- **묶음**: 기한 지남 / 이번 주 / 나중 / 완료(접기)
- **추가**: 맨 위 입력란에 한 줄로 쓰고 Enter. 기한과 우선순위는 행에서 고친다.

### 2-4. 버그

- **목록**: 심각도(`metadata.bug.severity`) 순으로 정렬한다.
  - 행: 심각도 배지, 제목, 상태, 발견 환경·버전, 등록한 쪽(나 / Claude / Hub)
- **상세**: task 상세 패널에 버그 정보 칸을 더한다. 재현 단계(`steps`), 기대 결과(`expected`), 실제 결과(`actual`), 환경(`env`), 버전(`version`).
- **"Claude에게 고치게"**: 일반 task처럼 실행되어 PR까지 간다.
- **버그 등록 창**: 제목, 심각도, 재현 단계, 기대·실제 결과, 환경, 버전, 저장소(여러 개일 때).
- **해결**: 완료된 버그는 "해결됨"으로 접는다. 히스토리에는 "버그 해결: …"으로 남는다.

### 2-5. 단계·배포

**단계**
- **흐름**: 앱의 단계 목록(`stages`)을 가로 흐름으로 보여 주고, 현재 단계를 강조한다. 기본은 기획 → 디자인 → 개발 → 테스트 → 배포 → 운영이다.
- **단계마다**: 그 단계로 표시된 task와 내 할 일 수(남은 것 / 전체), 그 단계에 들어온 날짜(히스토리의 "단계 이동")를 보여 준다.
- **단계 편집**은 설정 탭(2-8)에 있다.

**배포** (`GET /api/apps/:id/deployments`)
- **최근 상태**: 저장소 × 환경 표. 예: cyphers-meta의 frontend·backend × 운영.
  - 칸마다 상태 배지, 버전(태그나 짧은 커밋), 시각, 배포 주소 링크
- **배포 목록**: 최근 것부터 보여 준다.
  - 행: 시각, 저장소, 환경, 상태, 버전, 출처, 메모(워크플로면 커밋 제목)
  - 출처: Railway·Vercel(GitHub 배포 기록) / GitHub Actions / 직접 / Claude
- **필터**: 환경, 저장소
- **"배포 기록 남기기"**: GitHub에 남지 않는 배포를 직접 남긴다(예: 스토어 심사 제출). 환경, 상태, 버전, 메모를 받는다. 남긴 뒤 상태를 바꿀 수 있다(심사 중 → 성공).
- **"지금 가져오기"**: `POST /api/deployments/sync`. 평소에는 5분마다 가져온다는 안내를 붙인다.

### 2-6. 히스토리 (`GET /api/activities?app=`)

앱에서 일어난 일을 시간순으로 모은 기록이다.

- **모양**: 날짜로 묶고(오늘 / 어제 / 10월 25일), 줄마다 시각, 누가(나 / Claude / Hub / GitHub), 종류 아이콘, 문장을 보여 준다. 실제 예:

  ```
  10/27 15:54  GitHub  배포 성공 · 운영 260a2d7 (cypher-meta-frontend)
  10/27 13:43  Hub     TH-4 진행 중 → 리뷰: PR 생성 (run 4)
  10/26 22:44  나      기획 #1 승인: clamp 유틸리티 추가 → TH-2, TH-3
  10/25 22:40  GitHub  배포 성공 · 운영 backend-v0.1.32 (link): feat(admin): 회원 Premium …
  ```

- **종류 필터**(`kind`): task / 실행 / 기획 / 단계·앱 / 배포 / 메모 / 저장소
- **연결**: 줄을 누르면 연결된 것(task, run, 기획, 배포)으로 간다(`refType`, `refId`).
- **메모 남기기**: 위쪽 입력란(`POST /api/apps/:id/activities`). 예: "스토어 서류 준비 시작"
- **더 보기**: 아래로 내리면 이어서 불러온다(`before`).

### 2-7. 기획

v3 기획 인박스를 이 앱만 보이게 한 것이다. 새 앱 기획으로 만든 앱이면 맨 위에 "이 앱을 만든 기획" 카드를 둔다.

### 2-8. 설정

v3 앱 설정 상세를 옮기고, 아래를 더한다.

- **기본**: 소개(`description`), 기술 스택(`stack`), 링크(`links`, 이름 → 주소 목록).
- **진행 상태**(`lifecycle`).
- **단계 편집**(`stages`): 이름 바꾸기, 더하기, 빼기, 순서 바꾸기(끌기). "기본 6단계로 되돌리기"도 둔다.
  - 빼면 "이 단계에 묶인 task N개는 단계 없음이 돼요"를 확인받는다.
- **저장소** (`GET /api/apps/:id/repos`)
  - 목록: 이름, 경로, GitHub, 기본 브랜치, setup_cmd, 검사 명령(가드).
  - "저장소 다시 찾기"(`POST /api/apps/:id/repos/detect`), "저장소 추가"가 있다.
  - 저장소마다 **배포 워크플로 규칙**(`deployRules`)을 둔다: GitHub Actions 워크플로 이름 → 환경.
    - 처음에는 Hub가 이름으로 짐작해 넣는다. 예: "서버 배포" → 운영, "앱 배포 (안드로이드)" → 스토어.
    - "짐작한 값"이라는 표시와 바꾸기를 둔다.
  - 저장소에 명령을 비워 두면 앱의 setup_cmd·검사 명령을 쓴다는 안내를 붙인다.
- **v3에 있던 것**: 기본 브랜치, 작업 폴더 이름, setup_cmd, 가드(검사 명령), worktree 위치, 방향성 메모, 자동 생성 주기, 허용 도구, 실수 기록, Task Master 가져오기.

## 3. 기존 화면 수정

| 화면 | 바꿀 것 |
| --- | --- |
| 사이드바 | 1장대로 앱 → 앱 페이지, 점 색, 진행 상태, 보관 묶음 |
| 오늘 | 칸 두 개를 더한다. "운영 배포 실패"(저장소, 버전, 시각 → 배포 탭), "기한 지난 내 할 일"(체크로 완료). 처리할 일 순서에 넣는다 |
| 태스크 보드 | 종류 필터(기능 / 버그 / 잡무), 담당 필터(Claude / 나). 버그 카드에 심각도 배지, 내 할 일 카드는 체크 모양. 저장소가 여러 개인 앱은 카드에 저장소 이름 |
| task 추가 창 | 종류, 담당, 우선순위, 기한, 단계, 저장소(여러 개일 때) 칸. 종류가 버그면 버그 칸(2-4)이 펼쳐진다 |
| task 상세 패널 | 종류·담당·우선순위·기한·단계·저장소를 머리 정보에. 버그면 버그 정보 칸. 상태 버튼은 담당에 따라 다르다(내 할 일은 리뷰 없음) |
| 실행 상세 | 머리 정보에 저장소 이름. 실패 사유에 "push 전 검사 실패"(`failure: check`)를 더하고, 검사 명령 출력은 로그의 `check` 줄로 보여 준다 |
| 비용 | 앱별 칸의 앱 이름을 누르면 앱 페이지로 간다 |

## 4. 표시 이름

| 데이터 | 값 → 이름 |
| --- | --- |
| 진행 상태 `lifecycle` | developing 개발 중 · operating 운영 중 · paused 멈춤 · archived 보관 |
| 종류 `type` | feature 기능 · bug 버그 · chore 잡무 |
| 담당 `assignee` | claude Claude · me 나 |
| 심각도 `severity` | critical 치명 · high 높음 · medium 보통 · low 낮음 |
| 우선순위 `priority` | 1 높음 · 2 보통 · 3 낮음 |
| 환경 `env` | production 운영 · staging 스테이징 · development 개발 · preview 미리보기 · store 스토어 |
| 배포 상태 `status` | queued 대기 · in_progress 진행 중 · success 성공 · failure 실패 · cancelled 취소 · inactive 교체됨(새 배포가 나와 바뀐 예전 배포) |
| 배포 출처 `source` | github_deployment Railway·Vercel · workflow_run GitHub Actions · manual 직접 · claude Claude |
| 히스토리 주체 `actor` | me 나 · claude Claude · hub Hub · github GitHub |

## 6. 확인 기준

v4 시안 안에서 아래 흐름을 끝까지 따라갈 수 있으면 된다.

1. 사이드바에서 빨간 점이 붙은 앱을 누르고, 개요에서 원인(운영 배포 실패나 치명 버그)을 보고 그 탭으로 간다.
2. 버그를 등록하고 "Claude에게 고치게"로 실행해, 실행 상세로 간다.
3. 내 할 일을 한 줄로 추가하고 기한을 넣은 뒤, 체크해서 완료한다.
4. 단계·배포 탭에서 단계를 옮기고, 저장소 × 환경 배포 상태를 본 뒤, 스토어 심사 제출을 직접 기록한다.
5. 히스토리에서 배포만 걸러 보고, 메모를 하나 남긴다.
6. 설정 탭에서 단계 하나를 빼고(확인 창), 저장소의 배포 워크플로 규칙을 고친다.
7. 97일째 조용한 앱의 알림 띠에서 "멈춤으로"를 누르면, 사이드바에서 회색으로 바뀐다.
