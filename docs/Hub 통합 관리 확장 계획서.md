# Hub 통합 관리 확장 계획서 (제안)

Oct 27, 2026 · @suman

> 상태: X1(데이터와 API)과 X2(GitHub 연동)는 구현해 실제 Hub에 반영했다. X3(디자인 v4 앱 페이지)과 X4(대시보드 구현)가 남았다.

## 목표

Hub를 "Claude Code 작업실"에서 **내가 개발하는 모든 앱의 통합 관리 시스템**으로 넓힌다.

- **유지**: 지금 기능은 모두 그대로 둔다. task 실행과 PR, 기획과 새 앱 기획, 새 앱 시작, 규칙, 비용, hook과 MCP가 여기에 해당한다.
- **추가**: 앱 하나를 누르면 그 앱의 모든 것을 한 페이지에서 본다.
  - 앱 정보
  - 내가 할 일
  - 버그
  - 개발 단계와 배포 상태
  - 지금까지의 히스토리

## 결정

| # | 결정 | 내용 |
| --- | --- | --- |
| 1 | 할 일·버그 | **`tasks`를 확장한다.** 종류(기능, 버그, 잡무)와 담당(Claude, 나)을 더해, 개발 task·버그·내 할 일을 한 모델로 관리한다 |
| 2 | 개발 단계 | **기본은 고정 6단계**(기획, 디자인, 개발, 테스트, 배포, 운영)다. **앱마다 단계를 고치거나 더하고 뺄 수 있다** |
| 3 | 배포 기록 | **GitHub에서 자동으로 가져와** 배포 상태를 보여 준다. 수동 기록과 Claude 기록도 함께 받는다 |
| 4 | 히스토리 | **`activities`에 쌓는다.** 아래 "히스토리란" |
| 5 | 앱 상태 | **진행 상태(직접) + 자동 신호(Hub 계산).** 아래 "앱 상태는 무엇으로 정하나" |
| 6 | 앱 하나에 저장소 여러 개 | **`app_repos` 저장소 목록.** task마다 저장소를 고른다 |

## 확인하면서 찾은 것

### 앱 하나에 저장소가 여러 개다

| 앱 | 로컬 폴더 | 실제 저장소 |
| --- | --- | --- |
| LK Link | `~/project/link` | `suman-kim/link` 하나 (모노레포) |
| HR 하루알바 | `~/project/daily-work` (git 아님) | `daily-work-backend`, `daily-work`(frontend) |
| CM cyphers-meta | `~/project/cyphers-meta` (git 아님) | `cypher-meta-backend`, `cypher-meta-frontend`, `cypher-meta-app`(원격 없음) |
| TH, FJ | 각 폴더 | 저장소 하나 |

- **배포 상태**: 저장소마다 따로 확인해야 한다. 예를 들어 cyphers-meta는 frontend와 backend가 따로 배포된다.
- **지금 있는 결함**: HR과 CM은 앱의 저장소 경로가 git 저장소가 아닌 상위 폴더라서, **Hub runner로 task를 실행하면 worktree를 만들지 못하고 실패한다**. 기획 생성은 읽기만 하므로 지금도 된다.
- **제안**: 앱 아래에 저장소 목록(`app_repos`)을 둔다. task는 어느 저장소의 일인지 고를 수 있게 한다. 저장소가 하나뿐인 앱은 지금과 똑같이 동작한다.

### GitHub에서 배포 상태를 얻는 길은 두 가지다

| 출처 | 쓰는 저장소 | 얻는 것 |
| --- | --- | --- |
| **GitHub 배포 기록** (Railway, Vercel이 자동으로 남김) | cypher-meta-frontend 44건, cypher-meta-backend 29건, daily-work-backend 10건 | 환경 이름("Cyphers Meta / production"), 커밋, 상태(진행 중, 성공, 실패, 비활성), 배포 주소, 시각 |
| **GitHub Actions 워크플로** | link: "서버 배포"(`backend-v*` 태그로 실행), "앱 배포 (안드로이드)", "앱 프로덕션 출시 (안드로이드)" | 실행 결과(성공, 실패, 취소), 태그 버전(`backend-v0.1.32`), 커밋 메시지, 시각 |

- **연결 방식**: Hub는 맥북 안에서만 열려 있어 GitHub가 Hub를 직접 부를 수 없다. 그래서 Hub가 몇 분마다 `gh api`로 가져온다(pg-boss 주기 작업).
- **사용량**: GitHub API 한도(시간당 5,000회) 안에서 충분하다.
- **배포 기록 출처**: 위처럼 자동으로 남는 것이 있으면 바로 쓴다. 워크플로는 저장소마다 "어떤 워크플로가 어느 환경 배포인지"를 한 번 정해 준다(예: "서버 배포" → 운영 서버).

## 히스토리란

**앱에서 일어난 일을 시간순으로 모은 기록**이다. "이 앱이 지금까지 어떻게 진행됐는지", "언제 무엇이 배포됐는지", "버그가 언제 생기고 언제 고쳐졌는지"를 한 화면에서 거슬러 볼 수 있다. 처음 말씀하신 "개발과 배포가 어느 단계까지 진행됐는지 전체 히스토리를 관리"를 담는 탭이다.

지금 test-hub(TH)의 실제 기록으로 만들면 이렇게 된다.

```
10/27 13:43  TH-4 리뷰 대기: PR #3 생성 (run 4, $0.52)
10/27 13:43  TH-4 실행 시작
10/27 13:42  TH-4 생성: package.json에 description과 engines 필드 추가
10/26 22:45  TH-2 리뷰 대기: PR #2 생성 (run 3, $0.45)
10/26 22:44  기획 #1 "clamp 유틸리티 추가" 승인 → TH-2, TH-3 생성
10/26 22:43  기획 생성 (run 2, $0.60)
10/26 22:30  TH-1 리뷰 대기: PR #1 생성 (run 1, $0.53)
```

확장하면 여기에 다음 같은 줄이 더 들어간다.

```
10/25 22:36  배포 성공 · 운영 서버 backend-v0.1.32 (Link, GitHub Actions)
10/27 15:54  배포 성공 · Cyphers Meta / production 260a2d7 (Railway)
10/27 18:20  단계 이동: 디자인 → 개발 (FJ)
10/27 18:31  버그 등록: FJ-9 지각 판정이 1분 늦게 됨 (심각도 높음)
10/27 19:02  메모: 스토어 심사 서류 준비 시작
```

- **들어가는 일**: task 생성과 상태 변화, 실행과 PR, 기획, 버그, 단계 이동, 배포, 직접 남긴 메모.
- **보는 방법**: 종류별로 거르고(배포만, 버그만), 날짜로 묶는다.
- **저장 방법**: 일이 생길 때마다 Hub가 히스토리 테이블(`activities`)에 한 줄씩 쌓는다. 볼 때마다 여러 표를 합쳐 계산하는 방식보다 빠르고, 메모처럼 다른 표에 없는 기록도 넣을 수 있다. 지금까지의 기록(위 TH 예시)은 처음에 한 번 옮겨 넣는다.

## 앱 상태는 무엇으로 정하나

두 가지를 함께 보여 준다. **내가 정하는 진행 상태**와 **Hub가 자동으로 계산하는 신호**다.

**① 진행 상태 (내가 정함)**

앱을 계속 개발할지는 나만 안다. 그래서 고르게 한다.

| 상태 | 뜻 | 화면 |
| --- | --- | --- |
| 개발 중 | 지금 만들고 있다 | 사이드바 위쪽 |
| 운영 중 | 출시했고 유지보수만 한다 | 사이드바에 그대로 |
| 멈춤 | 잠시 손을 놓았다 | 흐리게 |
| 보관 | 더 하지 않는다 | 접힌 목록으로 |

**② 자동 신호 (Hub가 계산)**

| 신호 | 가져오는 곳 | 예 |
| --- | --- | --- |
| 배포 | GitHub 배포 기록, Actions 실행 결과 | "운영 배포 실패 · 2시간 전", "운영 ✓ backend-v0.1.32 · 2일 전" |
| 막힘 | Hub 실행 기록, 백그라운드 세션 상태 | "답변 대기 1", "실패한 실행 1", "세션이 허락을 기다림" |
| 버그 | Hub task (종류: 버그) | "심각한 버그 2" |
| 활동 | 마지막 커밋(GitHub·로컬 git), 마지막 세션·실행 | "14일째 조용함" |
| 단계 | 앱의 현재 단계 | "개발 (3/6)" |

**표시 방법**
- 사이드바의 앱 이름 옆 점 색은 가장 급한 신호 하나를 따른다.
  - 빨강: 배포 실패, 심각한 버그
  - 주황: 내 답이나 허락을 기다림
  - 파랑: 실행 중
  - 회색: 조용함
- 앱 페이지 개요에는 신호를 모두 줄지어 보여 준다.
- "개발 중"인데 14일째 조용하면 개요에 "계속할까요, 멈춤으로 둘까요?"를 띄운다.

## 앱 페이지

사이드바의 앱을 누르면 앱 페이지로 간다. 기능별 화면(오늘, 태스크 보드, 기획 인박스, 실행 기록, 비용, 규칙)은 모든 앱을 가로질러 보는 화면으로 남는다.

| 탭 | 보여 주는 것 |
| --- | --- |
| 개요 | 한 줄 소개, 진행 상태와 자동 신호, 현재 단계(진행 막대), 저장소별 최근 배포, 링크(GitHub, 운영 주소, 스토어, 문서), 숫자(열린 task·버그·내 할 일, 이번 달 비용), 최근 히스토리 5줄, 다음 할 일 3개 |
| 개발 | Claude가 실행하는 task (지금의 보드를 이 앱만) |
| 내 할 일 | 내가 직접 할 일. 기한, 체크, 단계 표시 |
| 버그 | 심각도, 상태, 재현 단계, 기대/실제 결과, 발견 버전·환경. "Claude에게 고치게"를 누르면 실행되어 PR까지 간다 |
| 단계·배포 | 이 앱의 단계 흐름과 단계별 남은 일. 저장소·환경별 배포 상태와 배포 목록(버전, 커밋, 상태, 시각, 주소) |
| 히스토리 | 위 "히스토리란"의 화면 |
| 기획 | 이 앱의 기능 기획 |
| 설정 | 지금의 앱 설정 + 저장소 목록, 단계 편집, 배포 감지 설정(워크플로 → 환경) |

## 데이터 모델 변경안

| 대상 | 변경 | 결정 |
| --- | --- | --- |
| `tasks` | `type`(feature, bug, chore), `assignee`(claude, me), `priority`(1\~3), `due_date`, `stage`(선택), `repo_id`(선택) 추가. 버그 정보는 `metadata.bug`(심각도, 재현 단계, 기대/실제, 환경, 버전) | 1 확정 |
| `apps` | `description`, `links`(JSON), `stack`, `stages`(JSON: 단계 목록, 기본 6단계), `stage`(현재 단계), `lifecycle`(개발 중, 운영 중, 멈춤, 보관) 추가 | 2 확정, 5 확인 중 |
| `app_repos` (새 테이블) | `app_id`, `name`(backend, frontend, app 등), `path`, `github`(owner/repo), `default_branch`, `setup_cmd`, `deploy_rules`(JSON: 워크플로 → 환경) | 6 확인 중 |
| `deployments` (새 테이블) | `app_id`, `repo_id`, `source`(github_deployment, workflow_run, manual, claude), `external_id`, `environment`(원래 이름), `env`(production, staging, development, preview, store), `version`(태그나 짧은 커밋), `sha`, `status`(queued, in_progress, success, failure, cancelled, inactive), `url`, `started_at`, `finished_at`, `raw` | 3 확정 |
| `activities` (새 테이블) | `app_id`, `at`, `kind`, `actor`(me, claude, hub, github), `ref_type`·`ref_id`, `summary`, `data` | 4 확인 중 |

**상태 흐름**
- **Claude가 하는 task와 버그**: 지금과 같다. `todo → doing ⇄ input → review → done`.
- **내 할 일**: `todo ⇄ doing → done`. todo에서 바로 done으로 갈 수도 있다.
- **Hub runner**: 담당이 Claude인 것만 실행한다.

**단계 편집**: 앱 설정에서 단계 이름을 바꾸거나, 더하거나, 빼고, 순서를 바꾼다. 이미 쓰는 단계를 빼면 그 단계에 묶인 task는 "단계 없음"으로 옮긴다.

## 입력은 어떻게 들어오나

| 경로 | 내용 |
| --- | --- |
| 화면 | 직접 등록하고 고친다 |
| Claude (MCP) | 새 도구를 더한다. `report_bug`(세션에서 버그를 찾으면 등록), `add_todo`(사용자가 직접 해야 할 일이 생기면 남김), `record_deploy`(GitHub에 남지 않는 배포를 기록, 예: 스토어 제출), `set_stage`(단계 이동). 규칙 파일에도 언제 부르는지 한 줄씩 넣는다 |
| Hub 자동 기록 | 실행, PR, 기획 승인, 새 앱 시작이 히스토리에 쌓인다 |
| GitHub (몇 분마다) | 배포 기록, Actions 실행, 태그, PR 머지. PR이 머지되면 task를 done으로 바꾼다 |

## 구현 결과 (Oct 28, 2026)

- **데이터와 API (X1)**

  - 처음 가져올 때 배포 90건을 48초 만에 가져왔다(cyphers-meta·하루알바의 Railway 배포, Link의 "서버 배포"와 앱 배포 워크플로).

- **v3 정본에 맞춘 서버 변경**
  - 비밀번호 로그인
  - push 전 검사 명령
  - 앱별 worktree 위치
  - Task Master 미리 보기와 덮어쓰기
  - 기획의 예상 비용, 바뀐 점 요약, 명세·영향 파일 목록, 원래 기획 링크
- **MCP 도구**: 12개(+`report_bug`, `add_todo`, `record_deploy`, `set_stage`). `hub.md`에 언제 쓰는지 적었다.
